# 小程序应用管理开发说明

第 3 阶段先交付 Rails 后台的应用管理，再接通微信授权与代码提审。一个机构可以接入多个小程序。先用微信实现完整流程，应用验收后再做 `links` 的 Banner 和菜单。用户登录、手机号绑定、支付退款和患者端页面随各自模块开发。

## 应用管理

| 超级管理员要做的事 | 页面和服务端行为 |
|---|---|
| 找到应用 | 「应用管理」提供列表、分页、详情。按名称或 AppID 搜索，按平台、运行状态筛选。列表显示 ID、应用平台、名称、AppID、微信授权、运行状态和创建时间。凭据配置情况在应用详情查看。运营和客服隐藏管理入口，直接请求页面及管理接口返回 403。以后运营在内容页选择所属应用时，选择器只返回所需标识和名称。 |
| 查看正式版小程序码 | 超管在微信应用行点击「二维码」后按 AppID 取正式版首页码。已授权使用授权方令牌；自有应用可用本应用生效的 AppSecret 直连。缺少凭据或微信拒绝时在弹窗说明原因。体验码仍从详情的当前体验版获取。登记应用、查看资料和自有密钥取正式版码均可独立于第三方授权；代上传、提审及发布要求目标 AppID 单独授权。 |
| 登记或改资料 | 保存平台、AppID、名称、备注和应用凭据。平台与 AppID 联合唯一，创建后在表单和服务端锁定。凭据未齐可以先保存为「已停用」。启用或进入审核中前核验本应用实际生效的接入凭据；明确区分已填写、已验证及平台暂不可达。 |
| 查看或更换密钥 | 超管打开配置页即见生效原值及来源。按「本应用加密数据库值 → 本应用环境变量 → 本应用 Rails credentials」读取，部署配置按平台和 AppID 精确匹配。留空或原样保存保留原来源，清除数据库覆盖后显示新的生效值。解密失败应报错；其他人已更换密钥时提示旧表单刷新。提交成功后使该应用的渠道令牌缓存失效。可参考[存储设置](../backend/app/services/storage_settings.rb)和[设置模块说明](设置模块开发说明.md)。 |
| 停用或恢复 | 停用只针对选中的应用。该应用的启动配置、新登录及已有会话的下一次业务请求均受服务端准入检查。恢复时，仍有效且属于该应用的会话可继续使用。保留用户、预约、支付和日志历史。以后支付模块处理存量交易回调、查单和退款时，按原交易核验。 |
| 删除录错的空应用 | 仅有本应用创建、编辑日志时允许删除，审计记录保留。有授权、发布或审核记录、用户身份或业务历史引用时，只能停用。以后若仅关联 Banner 或菜单，提示先移除内容再删除。用事务和已存在的数据库约束处理删除与首次使用并发，失败时提示阻止删除的原因。后续模块新增引用时同步补入保护。 |

应用字段基线见[数据库开发说明](../../预约挂号数据库文档/预约挂号开源版_数据库-开发说明.md)第 6.1 节。本轮已确认在原有 `active/disabled` 上增加 `auditing`，迁移的状态约束、模型、表单和筛选须一致。后续 `links.app_id` 引用应用主键，`user_apps` 通过 `(provider, appid)` 复合外键关联，预约的来源 AppID 与支付 AppID 保留作历史快照。终端按平台和 AppID 定位应用，用户权限另外由服务端验证。

## 微信提审与应用状态

应用有「正常」「审核中」「已停用」三种运行状态。超管可以在应用编辑页手动切换，提审流程也会自动更新同一个状态。授权表示微信允许后台代这个小程序执行哪些操作。发布记录描述一个版本上传、审核和发布的结果。一条发布记录可以多次提审，每次真实受理都要能按应用和微信审核单号追踪。现有数据库基线未包含第三方授权、发布记录和审核轮次，实施这一部分时在迁移及模块说明中列明新增记录、关联、唯一约束和删除行为。

以同院门诊 A、体检 B 为例：A 的 1.0 已上线，现在给 A 提交 1.1 审核。A 的两个版本在下次读取应用配置时都能读到「审核中」，B 始终沿用自己的状态和配置。审核中仍可使用小程序。首版先提供这个状态，登录引导、咨询等功能接入时再确定各项覆盖；覆盖仅对该应用的生效结果起作用，退出后重新读取正常配置。

| 动作 | 实施要求 |
|---|---|
| 授权与准备 | 超管从目标应用发起微信第三方平台授权，处理授权回跳、票据、令牌刷新和取消授权，确认授权归属于该 AppID。持应用 AppSecret 的直连能力与代上传提审各用对应凭据。后台展示缺少的授权或配置及可执行的下一步。 |
| 上传体验版 | 选择代码模板、版本号和说明，绑定目标应用，记录上传结果，可查看体验版。仅上传代码时保持应用原状态。再次提审同一份已上传代码时复用当前体验版，避免重复上传重新触发代码检测。 |
| 提交审核 | 针对当前体验版，记录操作者、本轮说明、是否审核通过后自动发布。发送提审请求前，使正常应用的「审核中」状态可被读到。微信受理后保存真实审核单号；明确未受理时排除该次尝试，按之前有效的审核轮次和应用状态恢复。超时、断线或本地写入失败可能发生在微信已受理之后，显示结果待核实，先核对远端记录再决定是否重试。 |
| 接收和查询结果 | 微信事件验签、解密并核对目标应用后交给任务处理。后台主动查询、定时补查和事件通知共用同一套结果处理。推送缺少审核单号时按该应用的真实轮次向微信核实。重复通知、任务重跑和迟到的旧结果只更新对应轮次。 |
| 结束审核与发布 | 审核延后仍为审核中。最新一轮通过、被拒或成功撤回后，仍处于审核中的应用恢复正常。超管中途停用时保留停用；旧结果不得结束更新的一轮。审核通过后支持手动发布，或按本轮已保存的选择自动发布一次。关闭或删除本地发布记录时，仍需追踪已提交微信的审核轮次。 |

人工登记、改密钥、启停、删除、授权、提审、撤回、主动同步和发布动作按[日志模块说明](日志模块开发说明.md)接入 `Log.record!`，并在 `Log::OPERATION_EVENTS` 登记。业务变更与成功审计一同提交，失败在回滚后记录。微信已受理而本地处理失败时分别保留两个结果。自动回调、轮询和发布结果在应用的发布记录中查看。日志用字段名表示密钥变更，过滤密钥、令牌、授权码和原始报文。

## 验收场景

1. 超管登记 A、B。运营和客服找不到管理入口，直接访问管理页、读配置或提交修改均被拒绝。A、B 使用不同来源的演示密钥。只改 B 的名称、原样提交密钥后，B 仍沿用原来源。轮换 A 的密钥仅刷新 A 的渠道令牌，审计可查且不含密钥。
2. A 上传 1.1 时仍正常；提审后 A 的 1.0 与 1.1 均读到审核中，B 正常。分别模拟微信明确拒收、受理后超时、审核延后、通过、被拒和撤回，检查应用状态、审核轮次及界面提示。重放回调和任务不会重复发布。
3. A 的旧结果晚于新一轮提审到达，新一轮仍在审核。超管在审核中停用 A，回调不能将 A 重新启用。先验证服务端按应用计算的准入及审核状态，再在真实终端接口接入时验证已有会话的下一次请求。后台仍可查 A 的历史，B 继续正常。
4. 刚建错且仅有创建日志的应用可删，删除后仍可查到是谁执行的。有授权或发布历史则给出原因并保留数据。`links`、用户身份、支付等模块落地时，分别补测关联保护和 A、B 隔离。

## 第 3 阶段实施记录

### 后台及部署

- 超管从侧栏「应用管理」进入 `/admins/apps`。编辑页维护状态与密钥，详情页发起授权、选择微信模板、上传、查看体验码、逐轮提审、查询、撤回与发布。人工操作可在「操作日志」按动作查询。自动任务的结果在应用详情的对应轮次查看。
- 应用凭据依次读取本行加密的 `apps.appsecret`、`MINI_APP_<平台大写>_<AppID原样>_APPSECRET`、credentials 中的 `mini_apps.<provider>.<appid>.appsecret`。例如部署键 `MINI_APP_WECHAT_wxDemoA_APPSECRET` 仅属于该微信应用。新建默认停用。启用时向对应平台验证实际凭据，验证摘要随凭据变化而失效。
- 微信第三方平台使用 `IntegrationSettings` 的 `wechat_component` 配置组。四项部署变量为 `WECHAT_COMPONENT_APPID`、`WECHAT_COMPONENT_APPSECRET`、`WECHAT_COMPONENT_TOKEN`、`WECHAT_COMPONENT_ENCODING_AES_KEY`。凭据文件中的对应字段为 `appid`、`appsecret`、`token`、`encoding_aes_key`。
- 在 `backend/` 执行 `bundle install` 和 `bin/rails db:migrate`，重启 Web 与 `bin/jobs`。两个进程使用相同的加密主密钥和 Redis 缓存地址，队列使用项目独立的 Sidekiq Redis。开发环境多进程联调设置 `REDIS_CACHE_URL` 后重启，使票据能在进程间读取。定时任务每 15 分钟补查，并补排最新通过轮次的自动发布。
- 微信授权事件接收路径为 `/api/wechat/component/events`，消息接收路径为 `/api/wechat/component/apps/$APPID$/messages`，浏览器回跳路径为 `/api/wechat/component/authorization/callback`。使用微信已登记的公网 HTTPS 域名从后台发起授权。推送校验时间戳、签名、解密尾部的平台 AppID，以及组件事件的平台标识或目标应用原始 ID。
- 终端启动配置读取 `GET /api/apps/:provider/:appid/configuration`，返回平台、AppID、名称和应用状态。停用应用返回 403。登录、手机号、支付、内容配置和患者会话在各自模块接入此边界。

| 迁移 | 写入、约束与删除 |
|---|---|

| `20261119032000_record_previous_wechat_review_state` | 提审时记录先前有效轮次是否仍在审，供本次未受理时恢复；后续补查旧轮的拒审说明也不会误改手动状态。 |

授权回跳按与浏览器会话绑定的 `state` 摘要查找发起超管的有效请求，再加锁一次性消费，同一超管在两个标签页分别给 A、B 授权时互不覆盖。

提交、撤回和发布先持久化本次操作的待核实状态，再发请求。明确拒收时记录微信错误码。连接中断、响应缺字段或微信确认后本地写入失败时，保留意图供补查。收到过微信确认时，人工失败审计分别列出远端结果与本地失败原因。应用级 PostgreSQL 会话锁串行化发布操作，终端可在发送提审时读取已提交的审核状态。

未取得提审单号时，超管先在微信后台核对 AppID、版本与时间。登记受理和发起发布都要核对该应用微信最新单的 `auditid`、`user_version` 与 `submit_audit_time`，并按审核单号复查状态。字段缺失、版本不符或提交时间落在本轮请求范围之外时保留待核实。老轮次缺少请求结束时间时，以原连接和读取超时限定核对范围。若新一轮未受理，恢复时核对先前有效轮次是否仍在审；已手动停用的应用保持停用。仅在微信核实未受理后登记未受理，才重新开放提审。发布请求超时后，系统先比较线上版本、发布前的版本信息和微信最新审核单。无法确定时继续保留待核实，自动任务不会再次发送。没有单号的通知只触发查询，每个结果只属于它自己的轮次。
