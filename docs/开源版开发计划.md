# 预约挂号开源版开发计划（讨论稿）

先在单机构、单后台的前提下，做出一份可以复制给其他项目的底板。用现有腾讯云 COS 验证设置，用微信支付验证收退款，用企业微信群机器人验证通知发送。底板可以独立运行后留一份干净版本，再从这个版本接入医院、号源和预约。每个阶段先讨论范围、使用者和完成标准，再决定字段、页面和代码写法。

## 当前进度

第 1 阶段设置底座的基本功能已验收，已接入存储和后台外观。第 2 阶段日志模块已通过设置与管理员操作验收，运营与客服可查看本人操作，超级管理员可查看全部操作记录。见[设置模块开发说明](设置模块开发说明.md)和[日志模块开发说明](日志模块开发说明.md)。

第 3 阶段已确定首批后端范围：先做应用管理和微信授权、提审与发布，再接用户身份及页面入口。目录、审核状态、验收场景和大雁参考路径见[小程序应用管理开发说明](小程序应用管理开发说明.md)。

- 当前 Rails schema 已有三张核心应用表 `admins`、`logs`、`settings`。管理员登录与管理、操作日志查询、存储配置和附件上传都已有实现。先对照目标补差，再接入新的调用方。
- 后台预约页使用示例记录，`miniapp/` 已初始化 Vue 3 工程和第一套首页入口，静态复刻待提供页面素材。排期要计入小程序和真实后台流程两端的工作。
- 开源版以 Word 的 16 张表、220 个字段和开发说明中的单机构规则为基线。Excel 用于核对用户动作和功能场景。商业版的合作伙伴后台、按医生划分的操作员权限、商品订单、积分和模拟预约量均已从首版范围移除。

## 第一部分  可复制的通用底板

| 阶段 | 开发内容 | 本阶段怎样算完成 |
|---|---|---|
| 1 设置 | 「系统设置」作一级菜单，各用途设二级页面，从现有「存储设置」接入。第三方接入参数沿用系统配置表 → ENV → Rails credentials 的优先级。业务模块定义各自的参数和校验。外观同时支持全后台默认和管理员个人偏好。 | 超级管理员打开系统设置即见生效原值，包括密钥。运营和客服看不到入口，服务端拒绝其读写请求。密钥加密入库，仓库和日志不含真实密钥。超级管理员能设定后台默认外观，管理员换设备登录后能沿用自己的选择。 |
| 2 权限、日志与后台公共能力 | 复用现有管理员登录、三类角色、日志入口、上传和公共页面组件。先拿“谁能改设置、谁能查看变更”走通服务端授权与审计。支付回调和队列任务接入时补上各自的日志上下文。 | 同一操作从页面或直接请求进入，权限结果一致。能查到谁在何时改了哪项设置，记录中看不到原始密钥。 |
| 3 小程序应用、用户与页面入口 | 接入 `apps`、`users`、`user_apps`、`links`，建立小程序入口、登录、手机号授权及按应用展示的 Banner、菜单。建议先跑通微信端，保留文档确定的平台身份边界。 | 可以打开一个小程序、登录并看到该应用自己的入口。同平台多应用只在身份可靠时共享用户，微信和抖音账号各自独立。 |
| 4 支付与退款渠道 | 约定发起支付、验证回调、查单、关单、退款及退款查询的调用方式，第一版实现微信。输入使用业务方提供的单号、金额和必要支付身份，输出调用结果或经校验的渠道结果。 | 用测试用例覆盖成功、重复回调和结果不明后查单。渠道代码可在没有预约表的情况下调用；重复入账与退款额度留给持有订单的业务在第 8 阶段验收。 |
| 5 通知发送 | 接入 `notifications` 和企微机器人。一条任务保存已选目标、消息、发送结果及重试信息。渠道配置用稳定标识，密钥由发送端按需读取。 | 给定目标和两条消息能创建任务、查看逐条结果。重试沿用原目标并跳过已确认成功的消息。发送端无需知道科室、医生或预约状态。 |

**留底节点在第 5 阶段结束。** 从一份干净副本启动后台，用部署者自己的配置完成登录、设置、上传、小程序入口验证，并能独立验证支付和通知调用。记录各渠道哪些场景已用测试验证、哪些已完成平台联调。此时保存可复制的版本，再进入下面的挂号开发。新项目沿用底板，按自身业务接收支付结果和决定通知目标。

## 第二部分  预约挂号业务

| 阶段 | 开发内容 | 本阶段怎样算完成 |
|---|---|---|
| 6 医院资料、就诊人、科室与医生 | 挂号模块接入医院资料和预约设置。开发 `patients`、`departments`、`doctors`、`doctor_departments`，打通后台维护及小程序医院首页、科室和医生查询、医生详情、就诊人管理。 | 后台维护的医生能在正确科室显示。用户只能管理自己的就诊人，同名就诊人可分别编辑。医生、科室和菜单图片复用已有上传能力。 |
| 7 排班、号源与免费预约 | 用 `schedules` 统一维护班次和有效日期，支持分时与非分时号源。落地 `appointments`，先打通选择医生、选时段、选就诊人、免费预约、查看记录与详情。下单时由服务端复核号源并保存快照。 | 后台排班后，用户能完成一次 0 元挂号。两人同时抢最后一个号只成功一次。修改医生资料后，历史预约仍显示当时的信息。 |
| 8 付费预约、退号与退款 | 将第 4 阶段的微信渠道接入预约。支持付费、待支付补付、关单、用户申请退号、审核、主动或部分退款及结果同步。预约、支付、退款三种状态分别维护，支付结果及退款明细按文档保存在 `appointments`。 | 一笔付费预约从付款走到退号退款。重复成功回调只记一次，渠道超时后用原单号核实；已退和处理中金额不会合计超过实付。取消后是否释放号源按已确认规则验收。 |
| 9 挂号事件通知与每日序号 | 接入第 5 阶段。挂号模块按事件从当前科室、祖先科室到医院默认选择机器人，再交给底板发送。用 `daily_counters`、`daily_sequences` 完成按用户、日期、机器人作用域发号。 | 同一用户当天在同一作用域登录或预约只领一次号。一次通知重试既不会重复发号，也不会改发其他群。可按发放记录核算月累计。 |
| 10 后台运营与开源交付 | 将预约预览替换为真实筛选、详情、完成、软删除、排班与预约导出，补齐小程序就诊提醒和已确认的咨询入口。分别确认预约量、接诊量、收入和退款的统计口径，整理单机构部署步骤。 | 用一套干净部署，从后台配置、排班、小程序挂号走到退款和通知。按角色验证查询、导出及退款权限，核对免费和付费记录的统计，确保公开示例只含演示数据。 |

## 各阶段开始前要讨论的决定

| 讨论时点 | 需要确定的事项 |
|---|---|
| 接入各类设置时 | 系统设置维护默认值，例外在对象自己的页面覆盖，清除后恢复继承。各模块接入时确定允许覆盖哪些项、谁能改、何时生效。见[设置模块开发说明](设置模块开发说明.md)。 |
| 做管理员与小程序时 | Word 中客服角色为 `support`，当前代码为 `customer_service`，账号字段及长度也有差异。先确定已有账号如何兼容、运营和客服分别能执行哪些操作。小程序确认首发平台及手机号授权流程。 |
| 做医院资料与排班时 | 确定就诊人年龄边界、医生展示规则、班次重叠的处理、限额为空和为零的含义，以及哪些状态占号、待支付占号多久。先用一位医生一天的排班把规则讲清楚。 |
| 做退款、通知和统计时 | 确定退号窗口、审核拒绝后的预约状态、再次申请与多次部分退款规则。确定各事件发给谁、登录没有科室时怎样选发号作用域，以及报表按哪个日期和状态统计。 |

每个阶段先用实际场景确认需求和待定规则，再整理目录安排、验收条件和交给实现 agent 的提示词。
