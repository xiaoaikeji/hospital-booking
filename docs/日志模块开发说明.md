# 日志模块开发说明

各模块通过 `Log.record!` 向 `logs` 追加记录，自行定义需要留存的事件。后台「操作日志」回答“谁做了什么、结果如何”。预约状态历史、支付交互等也使用这张表，分别在对应业务模块查看。

## 记录哪些操作

| 场景 | 记录方式 |
|---|---|
| 管理员停用账号、改配置、审核退款 | 记录操作人、时间、动作、对象和结果。保存成功只列实际变更的字段，例如仅清除 COS 地域就只记地域。涉及密钥只记字段名。 |
| 导出业务数据 | 即使业务数据没有变化，也要记录谁导出了哪一批数据，包括脱敏后的筛选范围、结果和实际导出数量。 |
| 打开页面、翻页、搜索、查看详情 | 首版普通浏览不记操作日志，包括客服查看就诊人详情。以后某种查阅确实需要留痕，由业务模块单独定义。 |

业务变更与对应的成功审计在同一事务提交。写入失败时，先回滚，再单独记录失败原因，并向操作人提示真实结果。例如外观保存失败提示“未保存”；存储配置已经保存、随后客户端刷新失败，则保留保存成功记录，另记刷新失败。日志摘要、异常及导出范围均须脱敏，避免写入密钥、原始请求或患者个人信息。

## 同一件事在哪里看

| 想查什么 | 页面与数据来源 |
|---|---|
| 谁点击了“同步退款状态”或“重试通知” | 在「操作日志」查管理员的操作事件，按操作主体和业务对象关联。 |
| 某笔预约经历了哪些状态，支付渠道返回了什么 | 在相应业务模块按预约查询 `logs` 的状态历史和脱敏交互摘要。实际收款金额、支付和退款状态以 `appointments` 为准，逐笔退款明细在 `refund_data.items`。 |
| 哪次通知发给了哪个目标，哪条消息失败了 | 在通知模块查 `notifications`。任务状态、消息和逐条回执归任务本身，人工重试的操作审计通过任务 ID 关联。 |

日志里的“成功”只说明该动作执行成功。例如查单成功表示拿到了查询结果，实际是否到账要看经过校验的支付结果。支付、退款和通知的具体页面随各自模块开发。

## 谁能查看操作日志

- 超级管理员可以查看全部**操作记录**。运营管理员、客服只看本人执行的操作，以当前登录管理员的 `actor_type` 和 `actor_id` 匹配。某人被修改、某笔预约由某人负责，都不等于操作由此人执行。
- 列表与详情先限定操作事件，再按角色限定范围。筛选、分页和直接输入日志 ID 都使用同一授权范围。支付回调、任务回执等技术事件留在对应模块，不能仅因共享 `logs` 就出现在操作日志页。

## 当前实现与下一步

写入入口在 [Log 模型](../backend/app/models/log.rb)。管理员账号、登录退出、系统设置和个人外观已有审计调用。[设置模块开发说明](设置模块开发说明.md)列出了保存失败和清除配置的具体行为。目前[操作日志控制器](../backend/app/controllers/admins/operation_logs_controller.rb)只允许超级管理员进入，列表从全部日志开始查询，详情按 ID 直接读取。

本阶段先收窄操作日志的数据范围，再开放运营和客服查看本人记录，并同步菜单权限。建议首版支持按时间、操作类型、结果筛选，超级管理员可另外筛选操作人。验收时让运营和客服各做一次操作，核对列表和详情均看不到对方的记录，再用超级管理员核对两人的操作都可见。另取一条支付回调样例，验证它不会混入操作日志。

## 新模块怎样接入

1. 用一个真实场景确定哪些动作需要记录、由谁触发、关联哪个对象、在哪个页面查看。支付、退款、通知各自定义事件，复用同一写入入口。
2. 用 `category` 区分业务、`action` 标识动作、`source` 标明来源。传入操作主体、目标和必要的脱敏摘要。预约相关支付和退款关联预约，退款再带上明细标识；通知操作关联任务。跨请求、任务和回调需要追踪时，沿用表中预留的关联标识。
3. 分别验收正常、失败和可见范围。保留业务主记录作为状态、金额、重试和防重复处理的依据。预约历史与支付交互按用途留存，具体归档期限随业务确认。

字段及合表依据见[数据库开发说明](../../预约挂号数据库文档/预约挂号开源版_数据库-开发说明.md)第 5.3、9 和 10.1 节。
