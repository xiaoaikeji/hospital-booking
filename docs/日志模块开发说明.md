# 日志模块开发说明

各模块通过 `Log.record!` 向 `logs` 追加记录，自行定义需要留存的事件。后台「操作日志」回答“谁做了什么、结果如何”。预约状态历史、支付交互等也使用这张表，分别在对应业务模块查看。

## 记录哪些操作

| 场景 | 记录方式 |
|---|---|
| 管理员停用账号、改配置、审核退款 | 记录操作人、时间、动作、对象和结果。保存成功只列实际变更的字段，例如仅清除 COS 地域就只记地域。涉及密钥只记字段名。 |
| 导出业务数据 | 即使业务数据没有变化，也要记录谁导出了哪一批数据，包括脱敏后的筛选范围、结果和实际导出数量。 |
| 打开页面、翻页、搜索、查看详情 | 首版普通浏览不记操作日志，包括客服查看就诊人详情。以后某种查阅确实需要留痕，由业务模块单独定义。 |

业务变更与对应的成功审计在同一事务提交。写入失败时，先回滚，再单独记录失败原因，并向操作人提示真实结果。例如外观保存失败提示“未保存”；存储配置已经保存、随后客户端刷新失败，则保留保存成功记录，另记刷新失败。日志摘要、异常及导出范围均须脱敏，避免写入密钥、原始请求或患者个人信息。

## 同一件事在哪里看

| 想查什么 | 页面与数据来源 |
|---|---|
| 谁点击了“同步退款状态”或“重试通知” | 在「操作日志」查管理员的操作事件，按操作主体和业务对象关联。 |
| 某笔预约经历了哪些状态，支付渠道返回了什么 | 在相应业务模块按预约查询 `logs` 的状态历史和脱敏交互摘要。实际收款金额、支付和退款状态以 `appointments` 为准，逐笔退款明细在 `refund_data.items`。 |
| 哪次通知发给了哪个目标，哪条消息失败了 | 在通知模块查 `notifications`。任务状态、消息和逐条回执归任务本身，人工重试的操作审计通过任务 ID 关联。 |

日志里的“成功”只说明该动作执行成功。例如查单成功表示拿到了查询结果，实际是否到账要看经过校验的支付结果。支付、退款和通知的具体页面随各自模块开发。

## 谁能查看操作日志

- 超级管理员可以查看全部**操作记录**。运营管理员、客服只看本人执行的操作，以当前登录管理员的 `actor_type` 和 `actor_id` 匹配。某人被修改、某笔预约由某人负责，都不等于操作由此人执行。
- 列表与详情先限定操作事件，再按角色限定范围。筛选、分页和直接输入日志 ID 都使用同一授权范围。支付回调、任务回执等技术事件留在对应模块，不能仅因共享 `logs` 就出现在操作日志页。

## 第 2 阶段实现现状

各模块继续通过 [`Log.record!`](../backend/app/models/log.rb) 追加记录，沿用原表和历史数据。[操作日志列表与详情](../backend/app/controllers/admins/operation_logs_controller.rb) 共用 `Log.operations_visible_to(current_admin)`。该查询先匹配 `source = admin` 和 `Log::OPERATION_EVENTS` 中登记的分类、动作组合，再按角色限定操作人。未能认证身份的登录失败记录保留给超级管理员查看。

| 已接入的操作 | 审计行为 |
|---|---|
| 管理员登录、退出 | 沿用登录、退出和登录失败审计。 |
| 新增、修改管理员及修改本人密码 | 账号变更和成功日志一同提交。成功摘要列出实际变更的字段，密码只记字段名。校验或数据库写入失败时，回滚后单独记录失败原因。 |
| 存储设置、全局和个人外观 | 复用[设置模块审计](设置模块开发说明.md)。重复提交同一存储密钥会保留原密文，清除配置只列实际删除的项。存储保存后刷新客户端失败时，用同一请求编号关联保存成功与刷新失败两条记录。 |

侧栏及顶部账号菜单向三种角色提供「操作日志」入口。列表支持按操作类型、结果、起止日期筛选，日期按北京时间计算，包含截止日。结果筛选、列表和详情统一显示「已开始」「成功」「失败」「已跳过」。超级管理员还可筛选操作人。分页与返回列表保留筛选条件。越权的详情 ID 和业务事件 ID 均返回 404。

[操作日志集成测试](../backend/test/integration/operation_logs_test.rb) 用运营、客服分别修改个人外观，并由超级管理员修改运营账号。测试覆盖本人操作、仅为被修改对象、不同主体类型使用相同 ID、筛选分页及详情直访。模拟支付回调留在 `logs`，三种角色均无法在操作日志列表或详情读取。

## 新模块怎样接入

1. 模块为每种事件确定 `category`、`action`、`source`、操作主体和业务对象，通过 `Log.record!` 写入。人工操作传入当前管理员及目标对象。需要在操作日志页展示时，将分类、动作和中文名称加入 `Log::OPERATION_EVENTS`，列表选项同步生效。
2. 支付回调使用 `source: "webhook"`，队列任务使用 `source: "job"`。支付和退款事件关联预约；退款另在 `details.refund_record_id` 记录明细标识。人工同步退款与渠道返回结果使用不同动作。人工重试通知关联通知任务，逐条回执在通知模块查看。跨请求、任务和回调的关联沿用表中预留字段。
3. 导出功能落地时记录操作人、结果、经过白名单脱敏的筛选范围和实际导出数量。普通浏览、搜索、翻页及查看就诊人详情跳过审计。业务模块只组装必要的安全摘要，避免传入原始请求、第三方报文、凭据或患者资料。
4. 接入时验证成功与失败、事务回滚、脱敏和跨角色可见范围。支付和退款的金额、状态、重试及幂等以业务主记录为准。

字段及合表依据见[数据库开发说明](../../预约挂号数据库文档/预约挂号开源版_数据库-开发说明.md)第 5.3、9 和 10.1 节。
