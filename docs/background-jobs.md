# Read-only task monitor

**后台任务** is visible and accessible only to super administrators. The current snapshot shows live processes, queue counts, scheduled jobs, retries and final failures. The history shows hourly recurring-task status, queue backlog and failure counts. Select a status cell to see that task's failures for the selected hour.

`BackgroundJobOverview.fetch` uses Sidekiq's API and the existing `REDIS_SIDEKIQ_URL` connection pool. `ProcessSet.new(false)` disables implicit process cleanup. No retry, clearing, deletion or queue mutations are exposed by routes or UI. Failure projections contain only task class, queue, time, retry count and exception class; arguments, exception messages and backtraces are excluded.

Recurring tasks are discovered from `config/schedule.yml`, and displayed queues come exclusively from Booking's configuration (`config/sidekiq.yml` plus `config/schedule.yml`). Currently only **默认队列** (`default`) is listed, even if other queue names such as `ai` or `media` exist in Redis; newly configured Booking queues appear automatically. An optional schedule `description` is used as the display label; otherwise known translations or the schedule name are shown. Last enqueue time comes from sidekiq-cron. Last completion and success/failure come from `CronResultRecorder`, registered in Sidekiq's server middleware.

The recorder matches configured worker class, queue and arguments. Ambiguous executions stay unattributed. The latest result remains in its dedicated Redis hash. A separate history stores recurring-task executions, observed exceptions and successful retries for 48 hours. An internal hash of the Sidekiq job ID connects a retry to earlier attempts. Worker return values and exceptions continue through the normal Sidekiq path when recording fails.

Sidekiq process beats capture queue counts once per five-minute bucket. The chart uses the last available sample in each of the latest 24 hourly buckets and leaves gaps where samples are missing. The failure chart counts exceptions in the hour they occurred, including attempts that later recovered. The current retry and final-failure table scans up to 1000 retry entries and the latest 20 final-failure entries, then shows at most 20 ordered by latest failure time. Totals cover the full sets.

Restart Sidekiq after deploying so queue samples and execution history start accumulating. The Web and Sidekiq processes share the same task Redis instance or logical database (`REDIS_SIDEKIQ_URL`), isolated from other projects and separate from cache Redis. The monitor starts with empty historical buckets and fills them as new executions and samples arrive.

The direct-account installation registers `notification_delivery` every minute on the default queue. Restarting the worker reconciles its schedule and removes the former managed-release, violation and result-notification cron entries. Existing fan and notification jobs retain their serialized class names. Review any previously queued managed-release work with its account owner before upgrading.
