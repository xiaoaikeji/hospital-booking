# 通知与公众号运营

超级管理员从侧栏「通知管理」进入医院业务通知、回复内容、微信模板消息和发送记录。渠道二维码和公众号自定义菜单位于「运营工具」。

场馆菜单与二维码共用回复、保留旧菜单文字、轮换原群机器人 Key 及两场活动复用绑定的操作，见[后台通知示例](setup/通知使用.md)。

## 配置回复

选择公众号，新增一组回复内容，在一页添加文字和小程序卡片、排序、预览并保存。卡片封面上传到当前公众号。菜单、渠道码、首次关注、再次关注和文字关键词均可引用同一组内容。

编辑页的「可用变量」可点击插入文字，右侧用示例值预览。支持粉丝昵称 `{name}`、用户编号 `{user_id}`、当前公众号名称 `{app_name}`、AppID `{appid}`、渠道码名称 `{qrcode_name}`、日期 `{date_new}`、星期 `{week}` 和互动时间 `{time}`。昵称未同步时显示「朋友」，用户编号未同步时显示「未同步」；渠道码名称只来自本次扫码，其他入口会省略包含它的整行。卡片保持管理员设置的固定内容。

保存时校验变量是否可用；需要原样显示 `{name}` 时填写 `{{name}}`。旧版本保存的回复继续按原文发送，重新编辑保存后启用变量替换。触发时保存替换后的实际文字，后续发送和补发均使用原快照。

菜单或渠道码的「新增回复内容」会打开编辑窗口；保存后返回正在编辑的入口并自动选中，父页面草稿保留。旧菜单中可读取原文的文字按钮可点「沿用原文字」带入回复草稿，线上菜单在发布成功后才切换。渠道码的「编辑回复」默认「仅改这个码」，保存时复制内容并自动绑定，原二维码保持不变；仅选择「更新全部」时显示已绑定的线上菜单、待核实菜单、渠道码、关注与关键词入口。菜单改绑在「保存并发布」确认成功后生效。

渠道码只填名称即可使用，默认仅统计来源；也可选择欢迎语、专属回复或两者。已关注粉丝再扫码按该码的配置处理，不改变原关注来源。欢迎语依首次／再次关注规则选择。扫码、菜单点击、关键词回调按公众号及微信事件标识持久去重。

首条文字可在微信回调中以加密 XML 应答，其余文字和卡片按顺序通过客服接口发送。记录中的「应答已生成」表示系统已生成回调应答，接收尚未确认；「渠道已接受」表示微信接口已确认接受，不表示已读。超时显示「待核实」，没有补发入口。

## 发送间隔

在「通知管理 → 回复内容」编辑时，可按分钟填写发送间隔。留空或填 0 表示不限，微信重复推送同一个事件仍只处理一次。

- **公众号回复**按公众号、粉丝和回复内容计算。例如同一个人点击菜单后又扫码，两处引用同一组回复，设为 5 分钟时只回复一次。另一位粉丝仍会收到，其他回复组也能正常发送。
- 从上次登记发送任务起算。间隔内的触发直接跳过，到期后由下一次新触发发送。一组里的多条消息仍按原顺序发送，人工补发仍只处理选中的失败条目。

## 企微群机器人

在「系统设置 → 企微通知设置」维护医院的默认机器人 Key。业务创建通知时固定收件群。切换默认群后旧任务仍投往原群；同一机器人轮换 Key 可显式迁移其待发目标。业务文字由事件字段渲染，超过 2048 字节时按完整 UTF-8 字符拆条，按原顺序分别记录发送结果。

### 医院业务通知

超级管理员打开「通知管理 → 医院业务通知」，选择事件并点「选择事件」。每个事件可保存一份文案，编排一至八条文字。点击「插入变量」可查看中文名称和虚构示例，在光标处插入。右侧预览与发送使用同一个渲染器。保存时校验变量，可选字段为空时省略所在行。勾选「启用此事件通知」并保存后，才会为新发生的业务结果登记消息。

| 事件 | 登记时机 | 此时可用的附加字段 |
| --- | --- | --- |
| 预约成功 | 免费预约确认落库，或收费预约经回调、主动查询确认收款并转待就诊 | 见下方订单字段 |
| 退号待审核 | 患者申请实际进入医院待审 | 退款字段、办理结果 |
| 退号已办理 | 患者申请获批、自动办理或医院主动退号使已确认预约取消 | 退款字段、办理结果、办理时间、取消时间 |
| 患者取消待支付预约 | 患者在付款期限内主动取消，确认未付款并关单。核实时等待；若查到收款则触发预约成功 | 申请来源、申请时间、办理结果、取消时间，无支付时间 |
| 退款失败需处理 | 整单退款或退差价经验证进入明确失败状态（微信关闭本次退款） | 退款字段、办理结果、办理时间、固定失败原因；退号单另有取消时间 |

所有类别提供事件名称和发生时间、预约号和状态、下单时间、平台、医院和地址、科室和医生、就诊日期和星期、班次、整班或分时、预约时段及分时起止时间。就诊人称呼、性别、年龄和联系电话尾号取自本单。支付字段包括挂号费、应付金额、已记录订单优惠、现金实付、支付状态和业务支付单号，以及适用的支付时间、付款截止时间。退款字段包括退款单号、申请类型和来源、原因、申请时间、申请金额、本次已确认现金实退、累计现金实退和剩余可退金额。编辑器按事件列出具体占位符。

收费退号提醒中的「预约已取消」表示已释放预约。退款金额以独立的资金结果为准。订单应付和现金实付分别展示，已确认零金额显示 0元，现金汇总不完整时注明待核对。退差价成功后保留就诊资格。拒绝退号、超时关单、医院取消未付款预约和暂时无法核实的渠道结果均不会触发相应的患者退号或失败提醒。

医院退号审核由 Booking 办理。微信小程序版本由微信开发者工具上传，在公众平台提审、查看结果。当前直连模式没有版本审核结果来源，配置机器人或创建模板无法自动通知版本审核通过或驳回。旧版发送记录仍可查阅。

## 微信模板消息

在当前公众号的「微信模板消息」选择微信已有模板，核对字段建议和示例预览，确认保存一次。相同事件以后直接使用已确认的模板和字段绑定，不在每次发送时重新猜测。业务决定收件人、真实数据、计划时间及跳转地址。

接入项目在 `config/initializers/notification_events.rb` 登记事件及业务字段；当前以「活动开始提醒」验证。同一个机构的其他公众号需分别配置，其模板、粉丝身份、素材和回复内容不会回退到另一账号。

```ruby
Notifications::TemplateMessages.new(account).deliver(
  event: "activity_start", subject: activity,
  recipients: [user_app], # 必须是当前公众号的已关注身份
  data: { activity_name: activity.name, starts_at: activity.starts_at },
  idempotency_key: "activity:#{activity.id}:start",
  scheduled_at: activity.remind_at,
  jump: { url: activity.public_url }
)
```

业务模型与收件人选择留在接入项目。模块不查询医院科室、电竞比赛或业务页面路径。缺字段、未绑定模板、跨账号收件人会拒绝登记；未到计划时间不发送。

## 通用发送入口

业务提供事件、业务对象、已选目标和实际消息。`dispatch` 返回 `Notification`；相同事件、业务对象、目标身份和去重标识返回原任务。无目标不建任务。消息 ID 在同一任务内唯一，补发不重新解析目标或生成内容。

```ruby
target = Notifications::Channels::WecomGroup.target(robot_key, name: "运营通知群")
task = Notifications.dispatch(
  event: "activity.reminder", subject: activity, target: target,
  messages: [{ id: "notice", type: "text", content: { text: "活动即将开始" } }],
  idempotency_key: "activity:#{activity.id}:reminder"
)
```

需要按业务数据替换文字时，先在 `Notifications::EventCatalog` 登记事件字段，再给 `dispatch` 传 `data: { 字段名: 本次真实值 }`；`messages` 中的 `{字段名}` 在登记任务时替换。未登记变量、必要字段缺失时拒绝登记；可选字段需显式声明 `optional: true`，空值省略整行。相同去重标识再次登记时返回原记录，不覆盖原内容。只供企微文案使用的事件登记为 `template_message: false`，不会出现在「微信模板消息」绑定列表。

Sidekiq 只传任务 ID。`Notifications::Delivery` 负责锁定执行、持久保存每条请求的发起状态及回执、汇总任务结果。渠道实现 `send_message(message, notification:)`，返回 `status: sent/failed/unknown`、安全的 `response` 与 `error_message`；第三方请求在各平台 Client。新增渠道只需增加渠道实现及模块内的选择，不改业务调用、控制器或 Worker。

企业微信按登记时选定的稳定渠道保存加密凭据。默认群由 A 改为 B 后，旧任务仍使用 A；若原群机器人更换了 Key，在「企微通知设置」勾选「为原群机器人轮换 Key」更新凭据后，原群待发和补发任务使用新 Key，且不能占用其他已登记通知群的 Key。渠道项缺失或身份不匹配时失败，不转发 B。正常发送与人工补发均保留原内容，机器人 Key 不进入任务快照或回执。

## 发送记录与补发

一次发送多条消息时，每条分别显示实际内容、处理步骤、次数及失败原因。文字成功、卡片被明确拒绝时，只补发卡片；已成功、已跳过及待核实条目不会再次发送。人工补发在操作日志中关联通知任务，并保留之前的尝试摘要。请求发出前先保存 `sending`，进程中断后定时恢复任务会将已发起请求的条目转为「待核实」，并继续发送尚未开始的后续条目。排队后关闭对应通知事件时，尚未发送的条目跳过，通用记录与原微信审核记录保持一致。

例如，一组有两条消息，第一条发送时管理员关闭通知。第一条保留实际回执，第二条显示「已跳过」。第一条已被渠道接受时，两处历史记录都显示「部分已跳过」。

`notifications` 保持已定的 16 个字段，消息与逐条结果在 JSONB 中，不新增消息子表或状态枚举。「待核实」使用逐条 `sending` 加渠道状态表达。医院模板按事件保存在 `hospital_notice.<event>` 设置项，渠道配置在 `settings.notification`；既有微信通知记录可在「发送记录 → 微信历史记录」查阅。

## 安装与升级

执行 `cd backend && bin/rails db:migrate`，然后重启 Web 和 Sidekiq。通用通知派发由 `config/schedule.yml` 每分钟补排到期任务。生产 Web 和任务进程使用相同的加密主密钥。

升级前产生的微信历史记录继续保留；它们没有目标快照，不伪造为新的通用任务。本次开发库没有这类记录。若其他部署已有旧的待发任务，升级前应核对目标并另行决定处理方式，不能推断其排队时的群。

本地测试使用模拟微信响应。上线仍需用医院自有公众号验证菜单发布、永久二维码、回调加密应答、客服窗口与卡片权限、真实模板字段限制及送达情况。
