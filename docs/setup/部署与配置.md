# 后端部署与配置

Web 和后台任务共用 PostgreSQL 与同一套加密密钥。任务队列和应用缓存分别配置 Redis。首次运行的初始化命令见[本地运行](本地运行.md)。

| 环境变量 | 用途 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL 连接 |
| `REDIS_SIDEKIQ_URL` | 生产任务队列（Booking 的 Web 与 Sidekiq 必须共用同一个、且与其他项目隔离的任务 Redis 实例或逻辑库） |
| `REDIS_CACHE_URL` | 生产缓存（需与任务 Redis 区分实例或逻辑库） |
| `RAILS_MASTER_KEY` | 解密部署环境提供的 Rails credentials，也可通过本机 `config/master.key` 提供 |
| `SECRET_KEY_BASE` | 生产 Rails 应用密钥，可通过运行环境提供 |

后台任务监控的队列列表仅读取 Booking 自身的队列与定时任务配置，但工作进程、延时、重试和最终失败总数来自整个任务 Redis。部署时务必让 Booking 的 Web 和 Sidekiq 指向同一个 `REDIS_SIDEKIQ_URL`，并与其他项目隔离（优先独立 Redis 实例，至少使用独立逻辑库），避免混入其他项目的进程或失败统计。

配置字段的加密密钥可通过 Rails credentials 的 `active_record_encryption` 分组提供，也可分别设置 `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY`、`ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY` 和 `ACTIVE_RECORD_ENCRYPTION_KEY_DERIVATION_SALT`。迁移数据库时需要保留原密钥，才能继续读取已有的加密配置。各部署环境单独保管自己的凭据与备份。

从仓库根目录构建后端镜像可执行 `docker build -t booking_web backend`。在目标环境准备好数据库、密钥和静态资源后，分别从 `backend/` 启动两个进程。

```sh
RAILS_ENV=production bin/rails server
RAILS_ENV=production bin/jobs
```

已有数据库首次升级小程序页面配置时，从 `backend/` 执行 `RAILS_ENV=production bin/rails db:migrate db:seed`。在 `miniapp/.env.production.local` 或发行构建进程中设置 `VITE_BOOKING_API_ORIGIN`，填写医院对外提供的 HTTPS 后台地址，并在每个微信小程序登记相应的 `request` 合法域名。HBuilderX 发行固定使用正式地址，轮播图和菜单图标也由该后台提供。[开发运行与预览的环境切换](本地运行.md#选择小程序后台)

## 使用 Capistrano 部署到自有服务器

Capistrano 用于把 `backend/`（管理后台与小程序 API）发布到医院自备的 Linux 服务器。微信小程序包仍沿用 HBuilderX 构建与微信开发者工具上传流程。头像、海报和附件的上传位置继续在管理后台「系统设置 → 存储设置」维护；选择本地存储时，文件保存在 `<deploy_to>/shared/storage` 并跨版本软链到 `current/storage`，再次发布后历史附件仍可正常读取。

每个版本把自己的静态资源清单保存在 `config/assets-manifest.json`，编译出的静态文件存放在共享目录 `<deploy_to>/shared/public/assets`，旧资源清理推迟到切流及健康检查全部通过后执行；部署失败或传入 `SKIP_SYSTEMD_RESTART=1` 跳过重启时，同样跳过本次清理，避免正在服务的旧页面缺少样式、脚本或图片。

### 配置职责划分

| 放在哪里 | 配什么 |
| --- | --- |
| 部署者本机（必填） | `ssh_target`（SSH 目标，支持本机 `~/.ssh/config` 别名，账号、端口与私钥位置自动沿用 `~/.ssh/config`）和 `deploy_to`（服务器发布根目录的绝对路径）。 |
| 部署者本机（可选） | `repo_url`（默认读取当前仓库 `origin`，源码 ZIP 下载无 `origin` 时手填）、`branch`（默认 `main`）、`web_service`（默认 `booking.web.service`）、`jobs_service`（默认 `booking.jobs.service`）、`cap_wrapper`（默认 `/usr/local/bin/booking-cap`）、`health_check_url`（默认 `http://127.0.0.1:3000/up`）、`systemd_use_sudo`（非 `root` 部署用户时设为 `true`）、`linked_files`（默认空，仅在改用 Rails credentials 密文时按需挂载）。 |
| 服务器环境文件 | `/etc/booking.web.env` 中的对外 HTTPS 域名（`APP_HOST`）、监听地址（`PUMA_BIND`）、PostgreSQL（`DATABASE_URL`，可附带 `?max_connections=10`）、任务与缓存 Redis（`REDIS_SIDEKIQ_URL`、`REDIS_CACHE_URL`）及 Rails 密钥（`SECRET_KEY_BASE`、`ACTIVE_RECORD_ENCRYPTION_*` 或可选 `RAILS_MASTER_KEY`）。Web、Sidekiq 与 `db:prepare` 共用同一份配置。 |
| Booking 管理后台 | 头像、海报、附件上传位置（「系统设置 → 存储设置」）以及微信账号、地图、企微通知、微信支付等业务配置。 |

公开仓库只提供通用部署脚本和空示例 `backend/config/deploy/production.local.yml.example`。本机真实配置文件 `backend/config/deploy/*.local.yml` 已加入 `.gitignore`。若缺少 `ssh_target`、`deploy_to` 或无法自动取得 `repo_url`，命令会在本机提示需要补齐的字段并中止，不会尝试建立 SSH 连接。

### 第一步：服务器首次环境准备（一次性）

以下默认使用独立的非 `root` 部署与运行账号 `booking`（所属用户组 `booking`）；若服务器仅使用 `root` 部署和运行，可按各步的 `root` 说明简化权限配置。

1. **安装基础软件、部署用户与 Ruby**：准备 PostgreSQL、Redis 7.0+（`maxmemory-policy noeviction`，开启持久化，任务与缓存使用不同实例或逻辑库）、Nginx、ImageMagick、`git`、`curl` 以及编译依赖（Debian/Ubuntu 可安装 `build-essential libpq-dev libyaml-dev pkg-config`）。创建部署与运行账号 `booking` 及发布目录，并为 `booking` 安装 `rbenv`、与 `backend/.ruby-version` 一致的 Ruby 版本（当前为 `3.4.12`）和 Bundler 4：

   ```sh
   useradd --create-home --shell /bin/bash booking
   mkdir -p /home/booking.capistrano
   chown -R booking:booking /home/booking.capistrano
   ```

   切换到 `booking` 用户安装 Ruby 与 Bundler（SSH 公钥也放在 `~booking/.ssh/authorized_keys`）：

   ```sh
   rbenv install 3.4.12
   RBENV_VERSION=3.4.12 gem install bundler -v 4.0.16
   ```

2. **创建服务器环境文件 `/etc/booking.web.env`（推荐纯环境变量方案）**：由 `root` 创建并仅对 `root` 与 `booking` 组开放只读权限（其他本机账号不可读）。不要把真实密钥提交到 Git，也不要在 shell 中直接 `source` 该文件。按以下格式填写（`KEY=value`，不加引号，`=` 两侧不留空格，注释以 `#` 单独占行）：

   ```text
   RAILS_ENV=production
   APP_HOST=booking.example.org
   PUMA_BIND=tcp://127.0.0.1:3000
   DATABASE_URL=postgresql://booking:CHANGE_ME@127.0.0.1:5432/booking_web_production?max_connections=10
   REDIS_SIDEKIQ_URL=redis://:CHANGE_ME@127.0.0.1:6379/0
   REDIS_CACHE_URL=redis://:CHANGE_ME@127.0.0.1:6379/1
   SECRET_KEY_BASE=REPLACE_WITH_OPENSSL_RAND_HEX_64
   ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY=REPLACE_WITH_64_HEX
   ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY=REPLACE_WITH_64_HEX
   ACTIVE_RECORD_ENCRYPTION_KEY_DERIVATION_SALT=REPLACE_WITH_64_HEX
   RAILS_LOG_LEVEL=info
   RAILS_MAX_THREADS=3
   SIDEKIQ_CONCURRENCY=3
   ```

   - **数据库连接池**：干净源码不包含 `backend/config/database.yml`，Rails 从 `DATABASE_URL` 解析连接配置。请直接在 `DATABASE_URL` 上附带 `?max_connections=10`（若已有 `?sslmode=require` 等查询参数，改用 `&max_connections=10` 拼接），并确保 `SIDEKIQ_CONCURRENCY` 不超过该连接池大小。不要依赖独立环境变量 `DB_POOL`。
   - **密钥生成**：使用纯环境变量时，可用 `openssl rand -hex 64` 生成 `SECRET_KEY_BASE`，用 `openssl rand -hex 32` 分别生成三把 `ACTIVE_RECORD_ENCRYPTION_*` 密钥。
   - **域名与端口**：`APP_HOST` 用于允许 `Host` 请求头（`/up` 与本机 `/up/deploy` 自动放行回环检查）和生成站内绝对链接。若同机已有服务占用 `3000` 端口，可改设 `PUMA_BIND=tcp://127.0.0.1:<空闲端口>`，并同步调整 Nginx 反代端口和本机 `health_check_url`。

   设置环境文件权限（普通部署账号 `booking` 需能读取它以运行 `db:prepare`、Puma 与 Sidekiq）：

   ```sh
   chown root:booking /etc/booking.web.env
   chmod 640 /etc/booking.web.env
   ```

   （若全程使用 `root` 部署和运行，可改设为 `chown root:root /etc/booking.web.env && chmod 600 /etc/booking.web.env`。）

   > **可选：改用 Rails credentials 存放配置与加密密钥**
   > 公开源码默认不包含 `config/credentials.yml.enc` 和 `config/master.key`。如果希望改用 Rails credentials 替代环境变量中的 `SECRET_KEY_BASE` 与 `ACTIVE_RECORD_ENCRYPTION_*`，请按以下三步配合：
   > 1. 将本地生成的密文文件传到服务器共享目录 `<deploy_to>/shared/config/credentials.yml.enc`（例如 `/home/booking.capistrano/shared/config/credentials.yml.enc`），权限设为 `chown root:booking ... && chmod 640 ...`（勿提交进 Git）。
   > 2. 在本机 `backend/config/deploy/production.local.yml` 中取消注释并启用：
   >    ```yaml
   >    linked_files:
   >      - config/credentials.yml.enc
   >    ```
   > 3. 在 `/etc/booking.web.env` 中填写 32 位十六进制解密主密钥 `RAILS_MASTER_KEY=...`（无需也不能把 `master.key` 放到 `<deploy_to>/shared/`）。

3. **安装环境注入脚本 `/usr/local/bin/booking-cap`**：Capistrano 的 `db:prepare`、Puma 与 Sidekiq 统一经该脚本读取 `/etc/booking.web.env` 并切换 `.ruby-version` 对应的 rbenv Ruby，避免密码中的特殊字符被 shell 展开。写入后执行 `chown root:booking /usr/local/bin/booking-cap && chmod 750 /usr/local/bin/booking-cap`（若仅 `root` 使用，设为 `chown root:root /usr/local/bin/booking-cap && chmod 750 /usr/local/bin/booking-cap`）：

   ```sh
   #!/usr/bin/env bash
   set -euo pipefail

   ENV_FILE="/etc/booking.web.env"
   if [ ! -r "$ENV_FILE" ]; then
     echo "booking-cap: cannot read $ENV_FILE" >&2
     exit 1
   fi

   orig_user="${USER:-$(id -un)}"
   orig_home="${HOME:-}"
   if [ -z "$orig_home" ]; then
     orig_home="$(getent passwd "$orig_user" 2>/dev/null | cut -d: -f6 || true)"
   fi
   orig_home="${orig_home:-/root}"
   orig_rbenv_root="${RBENV_ROOT:-$orig_home/.rbenv}"

   for var_name in $(compgen -e); do
     case "$var_name" in
       PATH) continue ;;
     esac
     unset "$var_name" 2>/dev/null || true
   done

   export HOME="$orig_home"
   export USER="$orig_user"
   export LOGNAME="$orig_user"
   export LANG="C.UTF-8"
   export LC_ALL="C.UTF-8"
   export RBENV_ROOT="$orig_rbenv_root"
   export PATH="$RBENV_ROOT/shims:$RBENV_ROOT/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"

   ruby_version="3.4.12"
   if [ -r ".ruby-version" ]; then
     parsed_version="$(tr -d '[:space:]' < .ruby-version)"
     parsed_version="${parsed_version#ruby-}"
     if [ -n "$parsed_version" ]; then
       ruby_version="$parsed_version"
     fi
   fi
   export RBENV_VERSION="$ruby_version"

   while IFS= read -r line || [ -n "${line:-}" ]; do
     line="${line%$'\r'}"
     if [[ -z "${line//[[:space:]]/}" || "$line" =~ ^[[:space:]]*# ]]; then
       continue
     fi
     if [[ "$line" != *=* ]]; then
       echo "booking-cap: missing '=' in $ENV_FILE: $line" >&2
       exit 1
     fi
     key="${line%%=*}"
     value="${line#*=}"
     case "$key" in
       *[!A-Za-z0-9_]*|[0-9]*)
         echo "booking-cap: invalid env key in $ENV_FILE: $key" >&2
         exit 1
         ;;
     esac
     export "$key=$value"
   done < "$ENV_FILE"

   exec "$@"
   ```

4. **配置 systemd 服务与受限 sudo 权限**：分别创建 `/etc/systemd/system/booking.web.service` 与 `/etc/systemd/system/booking.jobs.service`（注意把 `/home/booking.capistrano` 替换为实际的发布目录；若全程使用 `root`，把 `User=` / `Group=` 改为 `root` 且无需创建 sudoers 规则）：

   ```ini
   # /etc/systemd/system/booking.web.service
   [Unit]
   Description=Booking Web (Puma)
   After=network.target

   [Service]
   Type=simple
   User=booking
   Group=booking
   WorkingDirectory=/home/booking.capistrano/current
   ExecStart=/usr/local/bin/booking-cap bundle exec puma -C config/puma.rb
   Restart=always
   RestartSec=5

   [Install]
   WantedBy=multi-user.target
   ```

   ```ini
   # /etc/systemd/system/booking.jobs.service
   [Unit]
   Description=Booking Jobs (Sidekiq)
   After=network.target

   [Service]
   Type=simple
   User=booking
   Group=booking
   WorkingDirectory=/home/booking.capistrano/current
   ExecStart=/usr/local/bin/booking-cap bundle exec bin/jobs
   Restart=always
   RestartSec=5
   TimeoutStopSec=30

   [Install]
   WantedBy=multi-user.target
   ```

   以下均由 `root` 或具备完整 `sudo` 权限的系统运维账号配置。使用非 `root` 用户 `booking` 部署时，为 Capistrano 创建最小化的 `/etc/sudoers.d/booking-deploy`，仅授予日常发布所需命令（先用 `command -v systemctl journalctl` 确认二进制路径，部分系统为 `/bin/systemctl` 或 `/bin/journalctl`；写完执行 `chmod 440` 并用 `visudo -cf` 校验语法）。首次一次性启用服务的 `systemctl daemon-reload` 与 `systemctl enable --now` 不放进此规则，统一由运维账号执行：

   ```text
   booking ALL=(root) NOPASSWD: \
     /usr/bin/systemctl restart booking.web.service, \
     /usr/bin/systemctl is-active --quiet booking.web.service, \
     /usr/bin/systemctl restart booking.jobs.service, \
     /usr/bin/systemctl is-active --quiet booking.jobs.service, \
     /usr/bin/systemctl show -p MainPID --value booking.jobs.service, \
     /usr/bin/journalctl -u booking.web.service -n 30 --no-pager, \
     /usr/bin/journalctl -u booking.jobs.service -n 30 --no-pager
   ```

   ```sh
   chmod 440 /etc/sudoers.d/booking-deploy
   visudo -cf /etc/sudoers.d/booking-deploy
   systemctl daemon-reload
   ```

5. **配置 Nginx HTTPS 反向代理**：将医院对外 HTTPS 域名代理到 Puma（以 `127.0.0.1:3000` 为例），并直出 `current/public/assets/` 静态资源：

   ```nginx
   server {
     listen 80;
     server_name booking.example.org;
     return 301 https://$host$request_uri;
   }

   server {
     listen 443 ssl http2;
     server_name booking.example.org;

     ssl_certificate     /etc/nginx/ssl/booking.example.org.crt;
     ssl_certificate_key /etc/nginx/ssl/booking.example.org.key;

     root /home/booking.capistrano/current/public;
     client_max_body_size 50m;

     location ^~ /assets/ {
       expires max;
       add_header Cache-Control "public, immutable";
       try_files $uri =404;
     }

     location / {
       proxy_pass http://127.0.0.1:3000;
       proxy_set_header Host $host;
       proxy_set_header X-Real-IP $remote_addr;
       proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
       proxy_set_header X-Forwarded-Proto $scheme;
       proxy_set_header X-Forwarded-Ssl on;
     }
   }
   ```

   检查并重载 Nginx：`nginx -t && systemctl reload nginx`。

### 第二步：本机配置与首次发布

1. 在本地工作区的 `backend/` 下复制空配置示例并填写：

   ```sh
   cd backend
   cp config/deploy/production.local.yml.example config/deploy/production.local.yml
   ```

   在 `backend/config/deploy/production.local.yml` 中至少填写：

   ```yaml
   ssh_target: hospital-booking
   deploy_to: /home/booking.capistrano
   systemd_use_sudo: true
   ```

   - `ssh_target` 可直接填 `~/.ssh/config` 中的 `Host` 别名，账号、端口与私钥路径自动沿用本机 `~/.ssh/config`。
   - 若直接以 `root` 用户 SSH 部署，可将 `systemd_use_sudo` 保留为默认 `false`。
   - 若通过 ZIP 下载源码（本机无 Git `origin`），补充填写 `repo_url:`；若改用 Rails credentials，取消 `linked_files` 注释。

2. 首次发布（跳过服务重启、健康检查和自动清理旧资源，先落代码、装依赖、编译资产并初始化数据库）：

   ```sh
   cd backend
   bundle install
   SKIP_SYSTEMD_RESTART=1 bundle exec cap production deploy
   ```

3. 切换为部署运行用户 `booking`（若全程 `root` 部署则使用 `root`），核对连接池配置并显式设置密码创建首个超级管理员（不要在 `booking` 账号下执行 `systemctl enable --now`，首次启用放到下一步由运维账号完成）：

   ```sh
   cd /home/booking.capistrano/current

   # 确认从 DATABASE_URL 读取的连接池上限（应输出 10）
   /usr/local/bin/booking-cap bundle exec bin/rails runner \
     'puts ActiveRecord::Base.connection_db_config.max_connections'

   # 交互式无回显输入首个超级管理员密码（禁止留空、全空白或使用公开默认密码 123456）
   /usr/local/bin/booking-cap bundle exec bin/rails admin:create
   ```

   - 如需指定首个超管用户名（默认 `admin`），可在命令末尾传 Rake 参数：`admin:create ADMIN_USERNAME=hospital_admin`。
   - 无交互终端的自动化脚本可通过标准输入喂入密码，避免密码出现在命令行参数、shell 历史或日志中：

     ```sh
     read -rs -p "Admin password: " ADMIN_PASS && echo
     printf '%s\n' "$ADMIN_PASS" | /usr/local/bin/booking-cap bundle exec bin/rails admin:create
     unset ADMIN_PASS
     ```

   - 已有管理员时重复执行会直接拒绝创建并保留原账号与原密码。

4. 切回 `root` 或具备完整 `sudo` 权限的服务器运维账号，执行一次性首次启用并启动服务，再验证 `/up` 与本机回环 `/up/deploy`（`root` 账号可直接省略 `sudo`）；完成首次启动后，日常发布继续使用 `booking` 账号和 `/etc/sudoers.d/booking-deploy` 中的受限权限：

   ```sh
   sudo systemctl enable --now booking.web.service booking.jobs.service
   sudo systemctl is-active booking.web.service booking.jobs.service
   curl -i --max-time 10 http://127.0.0.1:3000/up
   curl -i --max-time 10 http://127.0.0.1:3000/up/deploy
   ```

### 第三步：日常发布、回滚与常用运维

确认本地改动已推送到目标 Git 分支（默认 `main`）后，在 `backend/` 执行一条命令完成日常发布：

```sh
cd backend
bundle exec cap production deploy
```

该命令依次执行：提取仓库 `backend/` 到新 release → 挂载 `shared/storage` 等持久化目录 → 串行安装生产 gem（`--jobs 1`）→ 使用构建占位库完成 `assets:precompile`（清单写到该版本 `config/assets-manifest.json`）→ 经 `/usr/local/bin/booking-cap` 用真实库连接执行 `bin/rails db:prepare` → 切换 `current` 软链 → 重启 `booking.web.service` 与 `booking.jobs.service` → 每轮重读当前 `booking.jobs.service` 状态与 `MainPID` 并联合校验 `http://127.0.0.1:3000/up` 与 `http://127.0.0.1:3000/up/deploy`（确认响应来自本次发布的 Booking 版本、数据库可读且当前存活的 Sidekiq 进程已在本次重启后发出新鲜心跳并连上任务队列）→ 确认全部通过后才执行 `assets:clean[5]` 清理过期资源。

- **发布检查范围**：`/up` 保留作为轻量存活检查；`/up/deploy` 仅允许服务器本机直接回环访问（带 `X-Forwarded-For` / `X-Real-IP` 的外部代理请求统一返回 `404`）。
- **仅演练命令不连接真实服务器**：可执行 `bundle exec cap production deploy --dry-run`（需已填写 `production.local.yml` 或传入 `DEPLOY_SSH_TARGET` / `DEPLOY_TO`）。
- **只发代码暂不重启服务**：`SKIP_SYSTEMD_RESTART=1 bundle exec cap production deploy`（会同时跳过健康检查与本次自动 `assets:clean`，保留旧版页面仍在使用的样式与图片，留待下次正常发布并通过健康检查后再清理）。
- **回滚代码版本**：`bundle exec cap production deploy:rollback`（仅回滚代码与该版本的 `config/assets-manifest.json`，不回滚数据库结构；若本次包含删表、删列等不兼容迁移，需先评估数据库兼容性）。
- **在服务器上执行 Rails 命令**：先 `cd <deploy_to>/current`，再通过 `/usr/local/bin/booking-cap bundle exec bin/rails console` 或 `runner` 执行，确保加载与线上一致的环境变量和 Ruby 版本。

## 接入医院自有微信账号

1. 超级管理员进入「应用管理 → 应用列表」，选择「微信」，再选「小程序」或「公众号」。逐个登记医院自己的 AppID、名称和 AppSecret。启用时后台验证该账号的凭据。微信要求 IP 白名单时，登记 Web 和任务进程的公网出口 IP。
2. 公众号还要在编辑页填写原始 ID（以 `gh_` 开头）、回调 Token 和 43 位 EncodingAESKey。复制此账号页面显示的 HTTPS 服务器地址到微信公众平台，选择 XML 和安全模式，填写相同的 Token 与密钥并启用。地址格式为 `/api/wechat/official_accounts/<AppID>/messages`。每个公众号单独配置一次。反向代理应正确传递外部域名和 HTTPS 协议。
3. 在「运营工具 → 渠道二维码」选择该公众号，创建「大厅」等渠道；在「通知管理」配置回复和微信模板消息。「发送记录」可以核对扫码回复和模板任务。菜单、客服消息、模板等能力取决于账号类型、认证和微信实际授予的接口权限。
4. 企微群机器人属于全院设置，由超级管理员在「系统设置 → 企微通知设置」填写。部署默认值可用 `WECOM_WEBHOOK_KEY`。如果同一个机器人换 Key，勾选原机器人轮换，已有待发任务继续使用该群。

账号密钥优先读取应用编辑页的加密值，其次读取该账号的环境变量，最后读取 Rails credentials。环境变量格式为 `MINI_APP_WECHAT_<AppID>_APPSECRET`、`MINI_APP_WECHAT_<AppID>_CALLBACK_TOKEN` 和 `MINI_APP_WECHAT_<AppID>_CALLBACK_ENCODING_AES_KEY`，AppID 保持原大小写。credentials 使用 `mini_apps.wechat.<AppID>` 下的 `appsecret`、`callback_token`、`callback_encoding_aes_key`。环境变量由 Web 和 Sidekiq 同时加载。

## 微信小程序登录

从 `backend/` 运行 `bin/rails db:migrate`，为已有用户和应用身份增加 `sessions`、`login_profile` 和 `first_entry`。手机和电脑分别通过微信登录，Booking 为每台设备签发 30 天的凭证。在「我的」退出后，该设备恢复游客状态。

登录后，在「我的」点头像，从微信原生面板选微信头像或相册图片。点名字，在微信键盘上选昵称或自行填写，完成后自动保存。后台「客户列表」显示同一份资料。未填写昵称时显示平台默认名，例如「微信用户243」。未设置头像时，圆头像显示昵称或默认名的第一个字。头像使用后台配置的存储。部署微信小程序时，将 Booking 的 HTTPS 接口域名加入 request、uploadFile 和 downloadFile 合法域名。

超级管理员在「系统设置 → 预约设置」维护「预约前验证微信手机号」，默认关闭。微信登录、打开「我的」和刚进入「预约挂号」表单都无需授权手机号。用户选好时段、填好就诊资料并点击「确定预约」时，表单重新读取本人资料。开关关闭或账号已验证时，直接校验本次联系电话。开关开启且账号尚未验证时，原页显示「验证账号手机号」，用户再点这个按钮才会打开微信原生授权面板。

验证成功后，Rails 将微信确认的号码和验证时间写入当前登录账号。表单保留医生、时段和就诊资料。仅当本次联系电话为空时才回填账号号码，已填的家属号码原样保留。取消或拒绝后可重新点「确定预约」，授权或换号失败可在原页重试。验证成功后由用户再次点「确定预约」。真实 AppID 目前会提示「医院预约受理尚未开放」，这个步骤不会创建预约、扣号或支付。游客 AppID 的模拟预约只保存在本机。

在「应用管理 → 小程序用户共享」为已在微信开放平台核实属于同一账号的小程序选择同一共享组。默认选项为「独立登录」。应用迁移到另一个开放平台时，先停用并移出原组，再核实新归属。首次入组或移出原组时，系统清理该应用的旧 UnionID，用户下次登录时重新取得。已有用户的 OpenID 绑定和预约归属继续沿用。两项设置的保存结果都可以在「后台管理 → 操作日志」查看。

离线退出会立即进入游客状态。小程序重新联网或回到前台后，会用保留的注销凭据补办该设备的注销。遇到「账号已停用」，小程序清理本机登录状态和本人资料。整应用停用进入「当前小程序已暂停服务」页。普通断网保留登录状态。会话到期时，并发读取共用一次续登，预约和支付仍需用户确认。

### 登录资料与 IP 归属地

超级管理员在「系统设置 → 地图服务」选择服务商，填写服务端密钥。页面显示生效值的来源。后台保存的密钥会加密，优先于环境变量及 Rails credentials。清除本页系统配置后，系统依次使用这两种部署来源。服务商默认使用百度，旧版已配置的百度 AK 可继续使用。

| 配置 | 环境变量 | Rails credentials |
| --- | --- | --- |
| 服务商，可选 `baidu` 或 `tencent` | `MAP_PROVIDER` | `map.provider` |
| 百度地图服务端 AK | `BAIDU_MAP_AK` | `baidu_map.ak` |
| 腾讯地图 WebService Key | `TENCENT_MAP_KEY` | `tencent_map.key` |

百度需开通普通 IP 定位，腾讯需开通 WebService 的 IP 定位。使用 IP 授权时，把运行 Sidekiq 的服务器公网出口 IP 加入所选服务商的授权名单。Web 与 Sidekiq 共用部署密钥。反向代理应覆盖客户端传入的转发头，Rails 的 `config.action_dispatch.trusted_proxies` 应与实际代理范围一致。[百度普通 IP 定位](https://lbsyun.baidu.com/docs/webapi?title=locationip/ip-api-base) · [腾讯 IP 定位](https://github.com/Tencent/tencentmap-webservice-skill/blob/main/references/api-location-weather.md)

| 资料 | 取得时间和存放位置 | 核对方式 |
| --- | --- | --- |
| OpenID、UnionID | 微信登录换码后写入对应的 `user_apps`。UnionID 按微信实际回包保存。 | 按平台、AppID 和用户编号查该应用绑定。 |
| 进入场景、小程序码渠道 | 小程序分别读取 `options.scene` 和 `options.query.scene`，按后台地址和 AppID 在本机保留游客的首次有效入口。用户关掉小程序后再登录，仍会补报这次入口。 | 客户详情中各小程序分别显示 `first_entry` 的 `launch_scene` 和 `channel_scene`。服务端确认后清理本地待报记录，按同一事件标识去重。静默续登不增加来源事件。 |
| 型号、操作系统 | 微信设备接口返回的各字段首次有效时写入 `users.login_profile`。使用已有会话回到前台也会补录。 | 本人资料接口可核对 `device_model` 与 `operating_system`，开发者工具允许为空。 |
| 首个公网 IP、地区 | Rails 按可信代理解析请求地址并保存 `login_profile.first_ip`。Sidekiq 每五分钟派发待补任务，按服务商实际返回的字段写入 `login_profile.region` 的国家、省、市。 | 在「后台管理 → 后台任务」查看补查任务，在本人资料接口或客户详情核对地区。 |

缺少密钥、服务超时或额度不足时，地区可留空，用户仍可登录、绑定手机号和读取资料。切换服务商或补配密钥后，下一轮任务会采用当前配置补查空缺。已取得的地区会保留。

小程序只配置 AppID 和 HTTPS 后台地址。微信登录码和手机号授权码分别由 Rails 向微信兑换。真机联调需核对该 AppID 的 request 合法域名、手机号接口权限和原生授权面板。

### 在后台查找用户

从「客户管理 → 客户列表」按用户编号、昵称或已验证的账号手机号搜索，也可以按应用和账号状态筛选。同一账号使用多个应用时只显示一行。列表可查看使用的应用、首次来源、首次地区、登录次数和最近登录时间。详情按应用列出各自的来源和登录记录。

点「查看」核对首次地区、设备，以及各小程序的首次入口场景和渠道参数。客服按现有权限查看已验证的账号手机号，超级管理员还可查看应用身份的 OpenID 和 UnionID。家属的本次联系电话留在预约表单，游客模拟下单成功后随本机预约记录保存。

## 微信支付

医院使用自己的普通商户号。先在微信商户平台开通小程序支付，核实每个收款小程序的 AppID 与该商户号已绑定。AppID 由 Booking 的「应用管理」维护，OpenID 来自该小程序的登录会话。支付配置可以在医院准备收款时补齐，登录与浏览可独立使用。

超级管理员打开「系统设置 → 微信支付」，填写普通商户号、医院后台的公网 HTTPS 回调域名，并选择接口版本。回调域名只填来源地址，例如 `https://booking.example.org`。反向代理应允许微信向 `/api/wechat/pay/` 下的路径发送 POST 请求，并转发原始正文及 `Wechatpay-*` 请求头。

| 接口版本 | 商户平台材料 |
| --- | --- |
| V2 | 收款、查单、关单、查退款只需 32 位 APIv2 密钥。发起退款前补齐有效的商户 API 证书 `apiclient_cert.pem` 和配套私钥 `apiclient_key.pem`，用于双向 TLS。补证前收到的款也可原路退款。 |
| V3 | 32 位 APIv3 密钥、商户 API 证书序列号和配套签名私钥。验签可填写微信支付公钥 ID 与公钥 PEM，或有效的平台证书序列号与证书 PEM。 |

将完整的 PEM 文本粘贴到对应字段。页面向超管显示生效值及其来源。密钥、证书和历史配置材料加密入库，操作日志只记字段名。系统配置优先，其次是环境变量和 Rails credentials。使用部署配置时，credentials 统一放在 `wechat_pay` 下，环境变量名为 `WECHAT_PAY_` 加上下表字段名的大写形式。

| 用途 | 配置字段 |
| --- | --- |
| 共用 | `version`（`v2` 或 `v3`，默认 `v3`）、`merchant_id`、`notify_origin` |
| V2 | `v2_api_key`、`v2_certificate`、`v2_private_key` |
| V3 | `v3_api_key`、`merchant_serial`、`v3_private_key`、`verification_id`、`verification_pem` |
| V3 换证过渡期选填 | `backup_verification_id`、`backup_verification_pem` |

新单使用全站选定版本。旧单固定原商户号、版本、AppID、单号和回调地址，续付、查单、关单和退款使用该商户在该版本下最近配置的凭据。同商户换签名证书时，在原版本更新证书和私钥后保存，再切换版本或商户。保留原回调域名，备份数据库、Rails 加密主密钥和 `secret_key_base`。

清除系统配置后，新单从部署配置读取。部署中只留商户号等零散字段时，新单须等配置补齐。旧单仍可按原商户号和版本读取最近保存的完整配置，继续查单和退款。

更换商户号时，重新填写新商户的密钥和证书。V3 的商户签名材料和微信验签材料均从新商户平台取得。使用平台证书时，填写该商户对应的平台证书序列号和 PEM。[微信平台证书说明](https://pay.wechatpay.cn/doc/v3/merchant/4013053264)

微信分批切换验签方式时，将希望用于接口应答的材料填在主栏，另一套填在「备用验签材料」。Booking 按应答和通知的 `Wechatpay-Serial` 选择公钥或平台证书。过渡完成后停用备用材料并保存。商户签名私钥与微信验签材料分别轮换。[微信验签切换指引](https://pay.wechatpay.cn/doc/v3/merchant/4012154180)

「系统设置 → 微信支付」会显示最近一次 V3 签名错误、订单或退款记录不存在的接口提示，列出 HTTP 状态、验签结果和实际收到的签名头名称。标为“未经验证”时，按原单号补查。支付和退款金额以通过验签及业务核对的结果为准。[微信查单错误码](https://pay.wechatpay.cn/doc/v3/merchant/4012791900)

本版提供业务调用方法和微信回调入口。预约收款与退号退款将在预约模块接入。正式收款前，需在业务侧接入幂等处理，并用已绑定 AppID 的真机核对小额支付、退款和公网通知。[V2 支付通知](https://pay.wechatpay.cn/doc/v2/merchant/4011937152) · [V2 退款](https://pay.wechatpay.cn/doc/v2/merchant/4011939427) · [V3 小程序支付](https://pay.wechatpay.cn/doc/v3/merchant/4012791911) · [V3 退款](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)

## 从旧版升级与小程序发版

- 升级前备份 PostgreSQL、部署密钥和附件。核对旧版审核单、待发布版本，以及队列、重试集和定时集中的发布操作；有真实待办时，先由该账号的发布负责人在微信公众平台核实并接手，再停旧 worker。已有通知任务保留原发送目标。
- 从 `backend/` 运行 `RAILS_ENV=production bin/rails db:migrate`，部署并重启 Web 与 Sidekiq。升级保留历史发布、体验版本凭证、用户身份、操作日志和通知记录。已有授权中来源明确且唯一的公众号原始 ID 自动带入。每个账号补齐自己的密钥并切换微信服务器地址，再用真号验证收发。
- 在 HBuilderX 用目标 AppID 构建小程序，在微信开发者工具上传版本，在微信公众平台设为体验版、提交审核并发布。每个小程序单独登记 request 合法域名；包含网页链接时，同样在该账号下登记业务域名。
- 「应用详情 → 基本资料」可读取正式版首页码和已存在的体验版首页码。体验码由账号自己的令牌请求 `getwxacodeunlimit`，使用 `env_version=trial`。体验者、版本和扫码资格在微信公众平台管理。通用海报使用正式版页面路径及参数。[微信获取小程序码接口](https://developers.weixin.qq.com/miniprogram/dev/server/API/qrcode-link/qr-code/api_getunlimitedqrcode.html)

## 附件存储

默认使用本地存储。使用腾讯云 COS 时，由超级管理员在「系统设置 → 存储设置」填写 SecretId、SecretKey、地域和桶名。需要从部署环境提供默认值时，配置 `ACTIVE_STORAGE_SERVICE=tencent_cos` 及以下变量。

- `TENCENT_COS_SECRET_ID`、`TENCENT_COS_SECRET_KEY`
- `TENCENT_COS_REGION`、`TENCENT_COS_BUCKET`
- `TENCENT_COS_ENDPOINT` 为可选的 HTTPS API 地址。

后台填写的配置优先，清除后依次读取环境变量、Rails credentials。已有 COS 文件时，先迁移文件再变更桶或地域。
